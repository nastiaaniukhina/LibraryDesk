# Чекліст огляду коду

Перед прийняттям змін перевіряємо:

| № | Категорія | Пункт перевірки |
|---|---|---|
| 1 | Іменування | Ім'я методу пояснює його призначення без читання тіла методу |
| 2 | Іменування | Терміни в назвах збігаються з глосарієм проєкту |
| 3 | Іменування | Немає імен-затичок і зайвих синонімів |
| 4 | Обсяг | Кожна зміна виконує одну чітку задачу |
| 5 | Обсяг | Немає змін, не пов'язаних із поточним завданням |
| 6 | Дані | Немає магічних чисел, важливі значення винесені в константи |
| 7 | Дані | Для грошей використовується `decimal`, для дат `DateOnly`, для моментів часу `DateTimeOffset` |
| 8 | Дані | Стани представлені через `enum`, публічні колекції доступні лише для читання |
| 9 | Складність | Вкладеність, довжина методів і кількість параметрів не перевищують установлених меж |
| 10 | Помилки | Некоректний ввід обробляється належним чином, немає порожніх `catch` |
| 11 | Помилки | Винятки містять зрозумілі повідомлення |
| 12 | Документація | Для нових публічних членів є змістовні XML-коментарі |
| 13 | Тести | Для кожної нової гілки логіки є відповідний тест |
| 14 | Тести | Перевірені граничні значення періоду: до, на момент і після `DueAt` |
| 15 | Прибирання | Немає закоментованого коду та TODO без номера |
| 16 | Прибирання | Немає директив `#region` |

## Правила комунікації під час огляду

1. Зауваження формулюються до коду, а не до автора.
2. Кожне зауваження має бути конкретним і виконуваним. Наприклад, замість «незрозуміло» потрібно написати «винесіть значення `0.95m` у константу».
