
# Стандарт кодування проєкту LibraryDesk

## 1. Сфера дії, рівні обов'язковості та глосарій

### 1.1. Сфера дії

Стандарт поширюється на такі проєкти рішення LibraryDesk:

- `LibraryDesk.Core` — бібліотека логіки предметної області.
- `LibraryDesk.App` — консольний застосунок.
- `LibraryDesk.Tests` — проєкт автоматизованих тестів.

Стандарт не поширюється на:

- `LibraryDesk.Core/Legacy` — навчальний легасі-код для аудиту SOLID (ЛР 4), який не входить до складу застосунку.
- Теки `bin/` і `obj/` — згенеровані файли збірки.
- Автоматично згенерований код.

Дата набрання чинності: дата коміту зі стандартом.

Версія стандарту: 1.0.0.

Власник стандарту: Анюхіна Анастасія.

Зміни до стандарту вносяться окремими комітами відповідно до правил комітів, наведених у додатку Б.

### 1.2. Рівні обов'язковості

Кожне правило стандарту має один із чотирьох рівнів обов'язковості.

| Рівень | Наслідок | Рівень діагностики | Рівень у .editorconfig |
|---|---|---|---|
| ОБОВ'ЯЗКОВО | Збірка падає | error | error |
| ЗАБОРОНЕНО | Збірка падає | error | error |
| РЕКОМЕНДОВАНО | Зауваження на огляді коду | suggestion | suggestion |
| ДОПУСКАЄТЬСЯ | Зауваження не роблять | silent або правила немає | none |

Рівень ОБОВ'ЯЗКОВО застосовується до правил, порушення яких впливає на коректність, безпеку або підтримуваність коду.

Рівень ЗАБОРОНЕНО визначає практики, використання яких не допускається в проєкті.

Рівень РЕКОМЕНДОВАНО застосовується до правил, дотримання яких покращує якість коду, але не є критично необхідним.

Рівень ДОПУСКАЄТЬСЯ визначає варіанти реалізації, які не суперечать стандарту.

### 1.3. Нумерація та шаблон правила

Для ідентифікації правил використовуються такі префікси:

| Префікс | Категорія |
|---|---|
| N | Naming — іменування |
| F | Formatting — форматування |
| C | Comments — коментарі |
| D | Documentation — документація |
| S | Structure — структура |
| A | Architecture — архітектура |
| X | Особливості предметної області: строки видачі та прострочення |

Кожне правило має унікальний ідентифікатор, назву, формулювання, рівень обов'язковості та спосіб перевірки.

Шаблон запису правила:

- Ідентифікатор — унікальний код правила.
- Назва — коротке формулювання вимоги.
- Правило — опис того, що потрібно або заборонено робити.
- Рівень — ОБОВ'ЯЗКОВО, ЗАБОРОНЕНО, РЕКОМЕНДОВАНО або ДОПУСКАЄТЬСЯ.
- Перевірка — аналізатор із кодом правила, пункт чекліста або автоматизований тест.

### 1.4. Глосарій

Усі поняття предметної області мають узгоджені назви українською та англійською мовами. В ідентифікаторах коду використовуються англійські назви.

| Поняття | Ідентифікатор | Пояснення |
|---|---|---|
| читач | Reader | Довідник учасників, незмінний record |
| видача | Loan | Документ зі станом, агрегат |
| позиція видачі | LoanItem | Книжка + строк у днях + денний тариф |
| книжка | Book | Довідник об'єктів обліку |
| ISBN | Isbn | Код книжки, непорожній рядок |
| вільні примірники | CopiesAvailable | Кількість, не менше нуля |
| денний тариф | DailyRate | decimal, гривні за добу |
| строк у днях | Days | Ціле число, більше за нуль |
| кінцевий строк повернення | DueAt | Задається при переході Reserved → Issued |
| заброньовано | Reserved | Початковий стан видачі |
| видано | Issued | Книжки перебувають у читача |
| повернено | Returned | Кінцевий стан видачі |
| прострочено | Overdue | Строк минув, книжки не повернуто |
| скасовано | Cancelled | Бронь скасовано до видачі |
| архівна видача | ArchivedLoan | Перегляд завершеної видачі без методів зміни |
| політика плати | FeePolicy (IFeePolicy) | Правило розрахунку вартості позиції |
| сховище видач | ILoanRepository | Абстракція зберігання видач |
| сповіщувач | INotifier | Абстракція повідомлень |
| постійний читач | IsRegular | Ознака для знижки |
| студент | IsStudent | Ознака для студентської політики |
| дні прострочення | OverdueDays | Кількість днів прострочення |
| сума до сплати | Total | decimal, гривні, округлена до копійок |

**Не вживати:** `Client`, `Customer`, `User` (замість `Reader`), `Order`, `OrderLine` (замість `Loan`, `LoanItem`), `Manager`, `Helper`, `Utils`.

### 1.5. Версійність та внесення змін

Поточна версія стандарту — 1.0.0.

Зміни до стандарту повинні бути узгодженими з чинною архітектурою проєкту та оформлюватися окремими комітами з типом `docs`.

Після внесення змін необхідно перевірити відповідність стандарту за допомогою автоматизованих інструментів та перегляду коду.


## 2. Іменування

У проєкті LibraryDesk використовується єдина система іменування, заснована на конвенціях C#. Усі ідентифікатори записуються англійською мовою та повинні відображати призначення відповідного елемента.

### 2.1. Нормативні правила іменування

#### N-01. Іменування просторів імен

**Правило:** простір імен повинен відповідати шаблону `LibraryDesk.<Проєкт>.<Тека>` та збігатися зі структурою тек проєкту.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** узгоджені простори імен спрощують навігацію кодом і допомагають визначити розташування класу в архітектурі проєкту.

**Погано:**
```csharp
namespace LibraryDesk;
```

**Добре:**
```csharp
namespace LibraryDesk.Core.Lending;
```

**Перевірка:** IDE0130.

#### N-02. Іменування типів

**Правило:** класи, записи (`record`), структури (`struct`) та перелічення (`enum`) іменуються за PascalCase. Назва повинна бути іменником, а назви перелічень використовуються в однині.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** зрозумілі назви типів дають змогу визначити їх призначення без аналізу внутрішньої реалізації.

**Погано:**
```csharp
class loanitem
{
}
```

**Добре:**
```csharp
class LoanItem
{
}
```

**Перевірка:** IDE1006.

#### N-03. Іменування інтерфейсів

**Правило:** назви інтерфейсів повинні починатися з великої літери `I`, після якої використовується PascalCase.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** спільна конвенція дає змогу відразу відрізнити інтерфейс від класу та зрозуміти його роль.

**Погано:**
```csharp
interface LoanRepository
{
}
```

**Добре:**
```csharp
interface ILoanRepository
{
}
```

**Перевірка:** IDE1006.

#### N-04. Іменування приватних полів

**Правило:** приватні поля класів іменуються за шаблоном `_camelCase`, тобто починаються з нижнього підкреслення та малої літери.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** така конвенція дає змогу відрізняти поля класу від локальних змінних і параметрів методів.

**Погано:**
```csharp
private List<LoanItem> items;
```

**Добре:**
```csharp
private readonly List<LoanItem> _items;
```

**Перевірка:** IDE1006.

#### N-05. Іменування методів

**Правило:** методи іменуються за PascalCase. Назва повинна відображати дію або результат запиту. Для методів дій використовуються дієслова, для методів перевірки — конструкції на зразок `IsExpiredOn`, для обчислень — назви на зразок `TotalOf`.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** назва методу повинна допомагати зрозуміти його призначення ще до перегляду реалізації.

**Погано:**
```csharp
public decimal Calc(Loan loan)
{
}
```

**Добре:**
```csharp
public decimal CalculateTotal(Loan loan)
{
}
```

**Перевірка:** IDE1006 та чекліст перегляду коду.

#### N-06. Іменування асинхронних методів

**Правило:** назва асинхронного методу повинна закінчуватися суфіксом `Async`.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** суфікс дає змогу відразу визначити асинхронний характер операції та відрізнити її від синхронного методу.

**Погано:**
```csharp
public Task<Loan> GetLoan(int id)
{
}
```

**Добре:**
```csharp
public Task<Loan> GetLoanAsync(int id)
{
}
```

**Перевірка:** VSTHRD200 або чекліст.

#### N-07. Іменування властивостей

**Правило:** властивості іменуються за PascalCase. Для властивостей типу `bool` використовуються зрозумілі префікси `Is`, `Has` або `Can`.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** назви властивостей повинні чітко передавати інформацію про стан або характеристику об'єкта.

**Погано:**
```csharp
public bool Regular { get; set; }
```

**Добре:**
```csharp
public bool IsRegular { get; set; }
```

**Перевірка:** IDE1006 та чекліст перегляду коду.

#### N-08. Іменування констант

**Правило:** константи іменуються за PascalCase без додаткових префіксів або використання великих літер у всій назві.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** єдина конвенція робить назви констант узгодженими з іншими членами класу.

**Погано:**
```csharp
private const int MAX_LOAN_DAYS = 30;
```

**Добре:**
```csharp
private const int MaxLoanDays = 30;
```

**Перевірка:** IDE1006, налаштування `constants_pascal` в `.editorconfig`.

#### N-09. Іменування локальних змінних і параметрів

**Правило:** локальні змінні та параметри методів іменуються за camelCase. Назви повинні бути змістовними та відображати призначення даних.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** зрозумілі назви полегшують читання методів і зменшують ризик помилок під час роботи з даними.

**Погано:**
```csharp
decimal t;
```

**Добре:**
```csharp
decimal totalAmount;
```

**Перевірка:** IDE1006 та чекліст перегляду коду.

#### N-10. Використання однобуквених імен

**Правило:** однобуквені імена змінних допускаються лише для короткочасних лічильників циклів.

**Рівень:** РЕКОМЕНДОВАНО.

**Обґрунтування:** однобуквені назви ускладнюють розуміння призначення змінної, особливо в довгих методах.

**Погано:**
```csharp
decimal t = CalculateTotal(loan);
```

**Добре:**
```csharp
decimal totalAmount = CalculateTotal(loan);
```

**Перевірка:** чекліст перегляду коду.

#### N-11. Іменування колекцій

**Правило:** назви колекцій повинні використовувати форму множини та відображати тип елементів, які вони містять.

**Рівень:** РЕКОМЕНДОВАНО.

**Обґрунтування:** форма множини допомагає відрізнити окремий об'єкт від колекції об'єктів.

**Погано:**
```csharp
List<LoanItem> item;
```

**Добре:**
```csharp
List<LoanItem> items;
```

**Перевірка:** чекліст перегляду коду.

#### N-12. Іменування тестових методів

**Правило:** тестові методи іменуються за шаблоном `Метод_Умова_Результат`. Назва повинна описувати дію, умову та очікуваний результат тесту.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** зрозумілі назви тестів дають змогу визначити, яку поведінку системи перевіряє тест, навіть без перегляду його реалізації.

**Погано:**
```csharp
public void TestLoan()
{
}
```

**Добре:**
```csharp
public void NextStatusOf_Issued_ReturnsReturned()
{
}
```

**Перевірка:** чекліст; CA1707 вимкнено для проєкту Tests.

#### N-13. Іменування файлів

**Правило:** назва файлу повинна збігатися з назвою основного типу, який він містить. Один основний тип розміщується в одному файлі.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** така організація спрощує пошук класів і підтримку структури проєкту.

**Погано:**
```text
LoanService.cs
```
У файлі розміщено кілька незалежних основних типів.

**Добре:**
```text
LoanService.cs
Loan.cs
LoanItem.cs
```

**Перевірка:** SA1402, SA1649.

#### N-14. Іменування подій і делегатів

**Правило:** назви подій повинні позначати дію в теперішньому або минулому часі. Назви делегатів можуть закінчуватися суфіксом `Handler`.

**Рівень:** ДОПУСКАЄТЬСЯ.

**Обґрунтування:** узгоджені назви допомагають розрізняти події та обробники подій.

**Погано:**
```csharp
public event Action Change;
```

**Добре:**
```csharp
public event EventHandler LoanIssued;
```

**Перевірка:** чекліст перегляду коду.

#### N-15. Іменування параметрів узагальнених типів

**Правило:** параметри узагальнених типів іменуються літерою `T` або комбінацією `T` з назвою типу.

**Рівень:** РЕКОМЕНДОВАНО.

**Обґрунтування:** загальноприйнята конвенція полегшує розуміння узагальнених класів, методів та інтерфейсів.

**Погано:**
```csharp
class Repository<ItemType>
{
}
```

**Добре:**
```csharp
class Repository<TItem>
{
}
```

**Перевірка:** IDE1006 та чекліст.

#### N-16. Мова ідентифікаторів і доменні терміни

**Правило:** усі ідентифікатори записуються англійською мовою. Для понять предметної області використовуються назви, визначені в глосарії розділу 1.

**Рівень:** ОБОВ'ЯЗКОВО.

**Обґрунтування:** єдина термінологія запобігає появі різних назв для одного поняття та підтримує узгодженість коду.

**Погано:**
```csharp
public class Chytach
{
}
```

**Добре:**
```csharp
public class Reader
{
}
```

**Перевірка:** чекліст перегляду коду та звірка з глосарієм.

### 2.2. Таблиця заборон

У проєкті не допускаються назви, які приховують призначення елементів, порушують єдину термінологію або ускладнюють розуміння коду.

| Антипатерн | Приклад у коді Legacy | Як має бути |
|---|---|---|
| Ім'я-затичка | `var o` у BuildCsvReport; `text` | `loan`, `csvText` |
| Числа замість станів | `loan.Status = 1` | `LoanStatus.Issued` |
| Тип рядком | `readerType == "regular"` | Перелічення або словник політик |
| Беззмістовний суфікс | `LoanManager` | `LoanService` |
| Ім'я, що вводить в оману | `BuildCsvReport` записує файл і виводить дані в консоль | `BuildCsv` повертає рядок |
| Два обов'язки в імені чи методі | `Place` зберігає дані й надсилає лист | `Place` та окремий сповіщувач |
| Синоніми одного поняття | `Client` / `Reader`, `LoanLine` / `LoanItem`, `LoanFormStatus` / `LoanStatus` | Один термін із глосарія |
| Транслітерація | `Chytach`, `Knyzhka` | `Reader`, `Book` |
| Угорська нотація та числові суфікси | `strName`, `loan1`, `loan2` | `readerName`, змістовні назви |

Додатковий ілюстративний приклад:

| Антипатерн | Погано | Як має бути |
|---|---|---|
| Нечітка назва логічної властивості | `public bool Flag { get; set; }` | `public bool IsStudent { get; init; }` |

### 2.3. Пари «погано / добре»

Наведені приклади демонструють відмінності між невдалим іменуванням у навчальному Legacy-коді та узгодженими рішеннями в основній бібліотеці Core.

#### 1. Назва методу та типи параметрів

**ПОГАНО (Legacy):**
```csharp
public decimal Place(LegacyLoan loan, string readerType)
```

**ДОБРЕ (Core, LoanService):**
```csharp
public void Place(Loan loan, Reader reader)
```

Використання конкретних типів замість рядків робить код зрозумілішим і зменшує ризик передавання неправильних значень.

#### 2. Числові значення замість перелічень

**ПОГАНО (Legacy):**
```csharp
loan.Status = 1;
```

**ДОБРЕ (Core, Loan.Issue):**
```csharp
Status = LoanStatus.Issued;
```

Перелічення робить стани видачі зрозумілими та усуває необхідність запам'ятовувати значення числових кодів.

#### 3. Неоднозначні назви змінних

**ПОГАНО (Legacy):**
```csharp
foreach (var item in loan.Items)
{
    total += item.DailyRate * item.Days;
}
```

**ДОБРЕ (Core):**
```csharp
foreach (LoanItem item in loan.Items)
{
    total += item.Amount;
}
```

Явна назва типу та використання властивості `Amount` роблять призначення операції зрозумілішим.

#### 4. Відкритий доступ до колекції

**ПОГАНО (Legacy):**
```csharp
public List<LegacyLoanItem> Items { get; set; }
```

**ДОБРЕ (Core):**
```csharp
IReadOnlyList<LoanItem> Items => _items.AsReadOnly();
```

Інтерфейс лише для читання не дозволяє зовнішньому коду безпосередньо змінювати колекцію.

#### 5. Беззмістовний суфікс Manager

**ПОГАНО (Legacy):**
```csharp
class LoanManager
{
}
```

**ДОБРЕ (Core):**
```csharp
class LoanService
{
}
```

Назва `LoanService` краще відображає призначення класу як сервісу для виконання операцій із видачами.

#### 6. Назва методу не відповідає його поведінці

**ПОГАНО (Legacy):**
```csharp
BuildCsvReport(...)
```

Метод записує файл і виводить результат у консоль.

**ДОБРЕ (Core, LoanCsvReport):**
```csharp
LoanCsvReport.BuildCsv(...)
```

Назва `BuildCsv` відповідає операції формування CSV-тексту, а не виконанню додаткових дій.

#### 7. Неявне перетворення числа на рядок

**ПОГАНО (Legacy):**
```csharp
"" + total
```

**ДОБРЕ (Core, Program.cs):**
```csharp
total.ToString("F2", CultureInfo.InvariantCulture)
```

Явне форматування забезпечує передбачуваний вигляд числового значення та однаковий роздільник десяткової частини.

#### 8. Перевірка типу читача через рядки

**ПОГАНО (Legacy):**
```csharp
readerType == "regular"
```

**ДОБРЕ (Core, Program.cs):**
```csharp
policies[readerType]
```

Використання словника політик дає змогу відокремити правила розрахунку від умовних перевірок рядків.

#### 9. Неузгоджені назви ознак читача

**ПОГАНО (Legacy):**
```csharp
isRegularClient
```

**ДОБРЕ (Core, Reader / ReaderInfo):**
```csharp
IsRegular
```

Єдина назва ознаки відповідає глосарію та усуває різні варіанти позначення одного поняття.

#### 10. Дублювання понять у переліченнях

**ПОГАНО (Legacy):**
```csharp
LoanFormStatus
LoanStatus
```

**ДОБРЕ (Core):**
```csharp
LoanStatus
```

Один перелік станів усуває плутанину та спрощує роботу з переходами між станами видачі.

#### 11. Нечітка назва логічної властивості

**ПОГАНО (ілюстративно):**
```csharp
public bool Flag { get; set; }
```

**ДОБРЕ:**
```csharp
public bool IsStudent { get; init; }
```

Назва `IsStudent` відображає конкретну характеристику читача, тоді як `Flag` не пояснює призначення значення.

#### 12. Дублювання назв тек

**ПОГАНО (структура до рефакторингу):**
```text
Reporting/
Reports/
```

**ДОБРЕ (структура після об'єднання):**
```text
Reports/
```

Використання однієї теки для пов'язаних звітів усуває дублювання та полегшує навігацію проєктом.

## Додаток А. Структура проєкту

А.1. `LibraryDesk.Core`: уся логіка предметної області, без `Console`.

А.2. `LibraryDesk.App`: лише введення й виведення, посилається на Core.

А.3. Класи предметної області лежать у теці `Domain`, один тип на файл, ім'я файлу збігається з ім'ям типу.

## Додаток Б. Правила комітів

Б.1. Формат повідомлення: `тип: коротка суть` (Conventional Commits).

Б.2. Дозволені типи: feat, fix, docs, chore, style.

Б.3. Повідомлення в наказовому способі, один коміт відповідає одній завершеній зміні.

Б.4. Теки `bin` і `obj` до репозиторію не потрапляють.
