Стандарт кодування проєкту LibraryDesk
Версія: 1.0.0
Власник стандарту: Анюхіна Анастасія
Дата набрання чинності: дата коміту, яким стандарт додано до
основної гілки.
1. Сфера дії, рівні обов'язковості та глосарій
1.1. Сфера дії
Стандарт поширюється на такі проєкти рішення LibraryDesk:
- LibraryDesk.Core --- бібліотека логіки предметної області.
- LibraryDesk.App --- консольний застосунок.
- LibraryDesk.Tests --- проєкт автоматизованих тестів.
- LibraryDesk.Refactoring і LibraryDesk.Refactoring.Tests ---
  навчальні проєкти рефакторингу, якщо вони входять до поточного
  рішення.
Стандарт не поширюється на:
- LibraryDesk.Core/Legacy --- навчальний легасі-код для аудиту, якщо
  завдання прямо не вимагає його зміни.
- теки bin/ і obj/ --- згенеровані файли збірки;
- автоматично згенерований код.
Версія стандарту --- 1.0.0. Зміни до нього вносяться окремими комітами
типу docs та відповідно до розділу 9.3.

2.2. Приклади
Погано:
private List<LoanItem> items;
public decimal Calc(Loan loan);
public bool Flag { get; set; }
loan.Status = 1;
Добре:
private readonly List<LoanItem> _items;
public decimal CalculateTotal(Loan loan);
public bool IsStudent { get; init; }
loan.Status = LoanStatus.Issued;
Погано: Client, Customer, LoanLine, Manager, Helper.

Добре: Reader, LoanItem, LoanService --- якщо назва відповідає
реальній відповідальності типу.
2.3. Правило var
var допускається, коли тип очевидний із правої частини, наприклад
var loan = new Loan(...). Для числових значень і виразів, де тип
неочевидний, потрібно вказувати тип явно. Для вбудованих типів проєкт
віддає перевагу явному типу відповідно до .editorconfig.

Перевірка довжини рядків:
.\scripts\check-line-length.ps1
У репозиторії має бути .gitattributes із правилом:
* text=auto eol=lf

5. Метрики складності
Метрики використовуються як сигнал для перегляду коду, а не як
самостійна оцінка якості. Перевищення межі потребує спрощення або
поясненого винятку.

5.2. Правила спрощення
- Ранній вихід із методу допускається, якщо він робить основний
  сценарій зрозумілішим.
- Складні булеві умови потрібно розділяти на змістовні частини.
- Повторювану логіку слід винести в один метод, якщо це зменшує
  дублювання без створення зайвої абстракції.
- Вкладені if за можливості замінюються перевірками з раннім
  виходом.
- Довгі списки параметрів за потреби замінюються об'єктом параметрів,
  якщо параметри утворюють логічну групу.
5.3. Перевірка метрик
Під час перевірки CA1502 використовується конфігурація
CodeMetricsConfig.txt. Для демонстрації працездатності аналізатора
поріг можна тимчасово знизити до 1, виконати збірку та показати
діагностику. Після демонстрації файл обов'язково відновлюється:
dotnet build 2>&1 | Select-String "CA1502"
git restore CodeMetricsConfig.txt
Тимчасове значення 1 не є постійним порогом проєкту.
6. Структура коду та архітектура
6.1. Структура рішення
- LibraryDesk.Core містить предметну логіку та не залежить від
  консольного інтерфейсу.
- LibraryDesk.App відповідає за введення, виведення та взаємодію з
  користувачем.
- LibraryDesk.Tests містить автоматизовані тести.
- Проєкти тестів можуть залежати від тестованих проєктів, але
  виробничі проєкти не повинні залежати від тестів.
- Legacy використовується лише для завдань аудиту та не
  підключається до основного сценарію застосунку.

- Некоректні аргументи перевіряються на межі публічного API.

  ArgumentOutOfRangeException.

  InvalidOperationException.
- Порожній catch заборонений.
- Виняток не перехоплюється, якщо код не може його обробити, доповнити
  контекстом або коректно перетворити.
- Не можна приховувати помилку поверненням довільного значення, яке
  виглядає як успішний результат.

8. Тестування та перевірка змін
8.1. Вимоги до тестів
- Кожна нова гілка бізнес-логіки має відповідний тест.
- Перевіряються нормальний сценарій, граничні значення та некоректні
  дані.
- Тести не залежать від реального поточного часу: час передається явно
  або контролюється тестом.
- Тести не залежать від порядку виконання.
- Назва тесту описує метод, умову та очікуваний результат.
- Тести перевіряють спостережувану поведінку, а не приватну
  реалізацію.
- Для грошових обчислень перевіряються округлення та граничні
  значення.
- Для переходів станів перевіряються дозволені й заборонені переходи.
8.2. Мінімальна перевірка перед комітом
dotnet restore
dotnet build
dotnet test
dotnet format --verify-no-changes
.\scripts\check-line-length.ps1
Якщо команда не застосовується до конкретної гілки або навчального
етапу, це має бути зазначено в описі завдання, а не мовчки пропущено.
8.3. Критерії готовності змін
Зміна готова до злиття, якщо:
1. реалізує поставлене завдання;
2. не містить сторонніх змін;
3. проходить збірку та тести;
4. відповідає правилам форматування;
5. має потрібну XML-документацію;
6. не додає закоментованого коду або TODO без номера;
7. має зрозумілий коміт.

Відступ 1 --- дужки. Runtime допускає пропуск дужок для однорядкових
блоків за визначених умов. Наш стандарт вимагає дужки завжди: у команді
початківців друга інструкція після if без дужок є типовим джерелом
помилки. Додатковий рядок коду є прийнятною ціною за однозначність.

Відступ 2 --- довжина рядка. Публічні настанови не встановлюють для
всіх проєктів однакової обов'язкової межі; Microsoft наводить 65
символів для прикладів у документації. У LibraryDesk встановлено межу
100 символів, щоб код залишався читабельним під час порівняння двох
версій у двох колонках. Це локальне правило проєкту, а не вимога
Microsoft або runtime.

Відступ 3 --- документація. Ми вимагаємо XML-коментарі для всіх
публічних членів Core. Публічні настанови не завжди вимагають однакового
рівня документації для кожного типу проєкту, але Core є бібліотекою
логіки, а CS1591 дає змогу автоматично виявляти відсутню документацію.
9.3. Порядок внесення змін
1. Будь-який учасник команди може запропонувати зміну через Pull
   Request до CODING_STANDARD.md.
2. Пропозиція містить формулювання правила, обґрунтування, приклад,
   спосіб машинної перевірки та оцінку вартості приведення наявного
   коду у відповідність.
3. Рішення ухвалює власник стандарту за принципом: правило має окупати
   втрату свободи зменшенням помилок, суперечок або часу читання.
4. Рішення фіксується записом журналу ЖР-NNN із датою.
5. Версія змінюється за семантичним версіюванням: нове сумісне правило
   --- 1.1.0, виправлення формулювання --- 1.0.1, несумісна зміна
   вимог --- 2.0.0.
6. Перехідний період: наявний код не переписується без потреби; до
   нового коду застосовується правило бойскаута, а борг із реєстру
   усувається до кінця семестру.
7. Шкідливе правило скасовується окремим записом у журналі зі статусом
   «скасовано» та датою.
9.4. Журнал рішень
ЖР-001. Момент округлення грошових значень
- Дата: дата ухвалення рішення.
- Контекст: політики округлювали значення по позиціях, тоді як
  Calculate округлював загальну суму.
- Варіанти: округлення кожної позиції окремо або округлення лише
  загального результату.
- Рішення: округлювати лише загальну суму відповідно до правила
  D-12.
- Наслідки: політики повертають неокруглені значення; потрібно
  оновити тести StudentFeePolicyTests.
- Статус: прийнято.
ЖР-002. Кінець періоду видачі
- Дата: дата ухвалення рішення.
- Контекст: умова now <= due у Loan.MarkOverdue не відповідає
  напіввідкритому інтервалу.
- Варіанти: змінити умову на now < due або залишити попередню
  умову як виняток.
- Рішення: використовувати now < due для перевірки, чи строк ще
  не настав. У момент DueAt видача вже вважається такою, для якої
  строк завершився.
- Наслідки: оновити тести граничних значень і опис у
  docs/model.md.
- Статус: прийнято.
Додаток А. Структура проєкту
- LibraryDesk.Core містить логіку предметної області та не залежить
  від консолі.
- LibraryDesk.App містить сценарій взаємодії з користувачем.
- LibraryDesk.Tests містить автоматизовані тести.
- Типи розміщуються у відповідних теках і просторах імен.
- Один основний тип розміщується в одному файлі з відповідною назвою.
Додаток Б. Правила комітів
Формат повідомлення: тип: коротка суть.

Дозволені типи:
- feat --- нова функціональність;
- fix --- виправлення помилки;
- docs --- документація;
- style --- форматування без зміни поведінки;
- refactor --- зміна структури без зміни поведінки;
- test --- додавання або зміна тестів;
- chore --- технічне обслуговування.
Один коміт має відповідати одній завершеній зміні. Повідомлення коротке,
конкретне та описує результат.

Теки bin/ і obj/, тимчасові файли, локальні налаштування IDE та
секрети не додаються до репозиторію.
